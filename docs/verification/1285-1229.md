## Verdicts

- **#1285: verified with caveats.** Hold, release, boot release, kernel facet,
  RPC and CLI behave as described. No regression found. Caveats: bugs 1 and 2.
- **#1229: verified with caveats.** The leak is gone, and gone with release too.
  One Known gap is misdescribed, and bug 1 is missing from its gaps.

## Bugs

1. **A kernel service's answer can be rolled back under a held result.**
   Pre-existing (#1168 class); the hold does not make it worse, but the caller
   now holds a kpid that protects nothing.
   - The service resolves through `KernelServiceManager.ts:299` with `immediate`
     true while another vat's crank is open. `#settleKernelSubscription` answers
     the caller at once, with the kpid. The crank aborts and rolls back the
     resolution, but not the `heldResult` row, which `#writeMessage` wrote
     outside any crank.
   - The caller has `{slots: ['ko2'], kpid: 'kp1'}`; `kp1` is `unresolved` again
     and `ko2` has reachable 0. The audit is clean, since nothing in the store
     claims the caller's kref. After `releaseResult(kp1)`, `kp1` stays
     unresolved forever.
   - Test: `holds an object handed to a queueMessage caller when a kernel
     service answers during a crank that aborts`
     (`packages/ocap-kernel/src/KernelQueue.kernel-service-abort.test.ts`, on
     both verify branches).
   - Fix direction: land the service's resolution between cranks, through
     `writeOutsideCrank`.

2. **Any `releaseResult` caller can end another caller's hold.**
   Comes with the new API.
   - kpids are sequential strings and `releaseHeldResult` does not check who
     calls. A second caller that names the first caller's kpid releases it, and
     the first caller's krefs are collected.
   - Test: `does not let one caller end the hold another caller was given`
     (`packages/ocap-kernel/src/KernelQueue.held-result.adversarial.test.ts`).
   - Fix direction: give the caller an unguessable receipt rather than the kpid,
     or scope `releaseResult` to the caller's own holds.

3. **Extension e2e tests assume a vat launch order** (pre-existing, test-only).
   A subcluster's vats launch in parallel, so which root gets `ko4`/`ko5`/`ko6`
   varies: traces show `ko4` as Alice on `main`, Carol on held-results, Bob on
   retire.
   - `object-registry.test.ts:83` selects option 1 and expects Alice.
   - The collect-garbage test clicks the last terminate button and expects `v3`;
     the trace shows it sent `terminateVat` for `v1`.
   - remote-comms messages a vat other than Alice, which has no `redeemer` in
     its baggage.
   - Also: when `loadExtension` throws in `beforeEach`, `afterEach` crashes on
     an undefined context (`control-panel.test.ts:20`), so `attachLogs` never
     runs and the kernel's logs are lost.

## Part 4: adversarial checks of the hold

Real store, queue and router, audit on; 16 tests, passing on both PR codebases
unless marked.

1. Abort after resolving a held result, then retry: hold, refcounts and answer
   consistent, for slots/data in either order across the abort.
2. Vat terminated mid-delivery: caller rejected, hold released, no row left.
3. Restart with an unsettled held result: released at boot, audit clean, the
   late answer settles without error, and its slots are then collected.
4. Out-of-crank resolution in an aborted crank: **fails**, bug 1.
5. Release outside a crank: promise deleted; `dropExports` and `retireExports`
   delivered without another message; nothing at refCount 0 after a restart.
6. Double release, and forged kpids (unheld promise, object kref, unknown kpid):
   throw, store unchanged. Another caller's kpid: **accepted**, bug 2.
7. Unresolved promise in an answer: kept until release, collected after.
8. System vat: `queueMessage` then `releaseResult` work across the kernel facet;
   a second release is refused.
9. `bootstrapResult` carries a kpid through `LaunchSubclusterRpcResultStruct`;
   released by the kernel for a system subcluster and when a peer vat fails.
10. CLI: decoded output drops the kpid; `--raw` shows it (unit test added; not
    run against a live daemon).

Tests: `packages/ocap-kernel/src/KernelQueue.held-result.adversarial.test.ts`,
`packages/kernel-test/src/held-result.adversarial.test.ts` with
`vats/held-result-vat.ts`, and a `--raw` case in
`packages/kernel-cli/src/commands/daemon.test.ts`.

## Part 5: retirement on #1229

- `lets a vat resend a settled imported promise it keeps in virtual data` fails
  on **all three** branches, by different mechanisms:
  - `main` and held-results: bob issues `syscall.resolve kp2` and is terminated
    with `"kp2" was already resolved`.
  - retire: bob is terminated with `p-1 is not an export reference`.
- `releases the returned object once its exporter is terminated` passes: the
  object lives while held, and is freed on `releaseResult` and on restart.
- The kernel-service-abort repro fails: bug 1.
- The extension remote-comms e2e takes its URL from the exported-URLs panel
  (`remote-comms.test.ts:95-107`), so the `ocapURLString` record is
  load-bearing there.

## Claims the code contradicts

- #1229 Known gaps and #1284 Out of scope: a vat that resends a settled imported
  promise from virtual data "is terminated once entries are retired". It is
  terminated on `main` too; retirement changes how, not whether.
- #1284, Why E: the kpid is one "only this caller was given, so a release cannot
  touch another holder's count". Bug 2.
- #1284, Why E: "no abort can roll it back from under a caller". True of the
  row, not of the value it protects. Bug 1. #1285's "the #1168 class is
  unchanged" understates this.
- #1229 Known gaps omits bug 1, which its own repro shows.

Suspicion, no test: a system vat that launches a subcluster through the facet
gets a `bootstrapResult` with a kpid; the node-runtime test vat never releases
it. Not among either PR's gaps.
